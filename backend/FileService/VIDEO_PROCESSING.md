# Обработка видео в FileService

## Поведение после загрузки

Для нового видео по умолчанию создаётся исходный ключ `videos/raw/{id}`.
Он хранится в `RawKey`; `Key` остаётся пустым до окончания обработки.

После завершения multipart-загрузки сервер одной операцией сохранения БД:

1. Переводит видео из `UPLOADING` в `UPLOADED`.
2. Создаёт связанный `VideoProcess` с четырьмя шагами в статусе `PENDING`.
3. Сохраняет процесс и шаги вместе с видео.

Завершение последнего шага устанавливает финальный `Key`, необязательный
`PreviewKey`, статус процесса `COMPLETED` и статус видео `READY`.
До этого API не выдаёт ссылку на скачивание. Исходный `RawKey` сохраняется.

`MediaAsset.RequiresProcessing()` — виртуальный метод. Для `PreviewAsset`
он возвращает `false`, для `VideoAsset` — `!DirectUpload`.
Локальное свойство `RowKey` переименовано в `RawKey`.

## Ключи и DirectUpload

| Поле | Назначение | Хранение в БД |
|---|---|---|
| `RawKey` | Исходник видео для обработки | Да, nullable |
| `Key` | Готовый файл | Да, nullable |
| `PreviewKey` | Превью обработанного видео | Да, nullable |
| `UploadKey` | Выбранный ключ загрузки | Нет, вычисляемое свойство |
| `DirectUpload` | Файл загружается сразу по финальному ключу | Да |

`UploadKey` выбирает `Key` при `DirectUpload == true` и `RawKey` в остальных
случаях. Флаг сохраняется на ассете, поэтому смена конфигурации не меняет ключ
уже начатой загрузки. Все операции multipart-загрузки используют `UploadKey`.

Настройка для **новых видео** в `FileService.Web/appsettings.json`:

```json
{
  "MediaUpload": {
    "DirectUpload": false
  }
}
```

При `true` видео считается подготовленным к воспроизведению: отдельный процесс
не создаётся, после загрузки оно получает `READY`. Изображения всегда используют
этот сценарий; их ключ по-прежнему имеет путь `preview/raw/{id}`.

`UploadId` в multipart API остаётся идентификатором сессии S3 и не заменяет ключ.

## Шаги

| StepType | Order | Weight | Прогресс после завершения |
|---|---:|---:|---:|
| `VALIDATE` | 0 | 10 | 10% |
| `TRANSCODE` | 1 | 65 | 75% |
| `GENERATE_PREVIEW` | 2 | 15 | 90% |
| `UPLOAD_RESULT` | 3 | 10 | 100% |

Это начальный набор шагов, поскольку конкретные типы и веса в конспекте не заданы.
Определения находятся в `VideoProcess.InitializeSteps()`.

Прогресс равен сумме весов завершённых и пропущенных (`SKIPPED`) шагов,
делённой на сумму всех весов и умноженной на 100. Это доля обработанных шагов;
пропуск не означает успешного выполнения. Выполняющийся или упавший шаг
не добавляет прогресс.

У шага есть GUID, тип, порядок, вес, статус, строка результата, сообщение ошибки,
время начала и окончания, число повторов и время следующей попытки.
`ResultData` хранится как текст: исполнитель может передавать JSON или другой
строковый результат.

## Управление и повторные попытки

`VideoProcessingService` зарегистрирован в DI как scoped-сервис:

- `ProcessNextStep(processId)` запускает первый незавершённый шаг.
- `CompleteCurrentStep(processId, stepId, attemptId, resultData, ...)`
  фиксирует результат. Для последнего шага обязателен `finalKey`;
  `previewKey` необязателен. Ключи исходника, результата и превью должны различаться.
- `FailCurrentStep(processId, stepId, attemptId, errorMessage, isCriticalFailure)`
  сохраняет ошибку и определяет возможность повтора.

Каждый вызов сохраняет состояние и пишет лог. Следующий шаг запускается
отдельным вызовом `ProcessNextStep`, когда исполнитель готов принять работу.

Для некритической ошибки предусмотрены **три повтора после первой попытки**,
то есть максимум четыре запуска шага. Задержки перед повторами: 30, 60 и 120 секунд.
До `NextRetryAt` запуск запрещён. При наступлении срока `ProcessNextStep` вызывает
`Reset`, увеличивает `RetryCount` и запускает ту же операцию заново.

Критическая ошибка либо исчерпание повторов переводит процесс и видео в `FAILED`.
Завершённые шаги и достигнутый прогресс сохраняются.

Каждый запуск получает новый `AttemptId`. Результат старой попытки отвергается.
Токен версии процесса предотвращает одновременное сохранение запуска двумя
обработчиками. При конфликте репозиторий возвращает `video.processing.conflict`;
следует загрузить актуальное состояние в новом scope.

## Автоматическое выполнение последовательности шагов

Проект `FileService.VideoProcessing` содержит сервис
`VideoProcessingService.ProcessVideoAsync(videoAssetId, cancellationToken)`.
Он возвращает `UnitResult<Error>` и запускает `IProcessingPipeline`.
Асинхронное имя сохранено вместо `ProcessVideoSync` из конспекта.
Существующий `Core.Processing.VideoProcessingService` остаётся API для ручного
управления отдельными шагами и их повторными попытками.

Регистрация инфраструктуры: `services.AddVideoProcessing()`.
Каждый реальный обработчик регистрируется через
`services.AddProcessingStep<THandler>()`. Для каждого `StepType` нужен ровно
один обработчик. Отсутствие или дублирование обработчика возвращает ошибку
до запуска соответствующего шага.

Pipeline загружает видео с процессом и шагами, создаёт отсутствующий процесс
через доменную фабрику и выполняет незавершённые шаги в доменном порядке.
Завершённый процесс повторно не выполняется. Ошибка загрузки не является
основанием для создания нового процесса.

`IProcessingStepHandler.ExecuteAsync` возвращает `ProcessingResult`:

- `Success(context, resultData)` — завершить шаг и сохранить его результат;
- `Failure(error, isCritical: true)` — сохранить ошибку и остановить процесс;
- `Failure(error, isCritical: false)` — сохранить ошибку со статусом `SKIPPED`
  и перейти к следующему шагу без повторной попытки.

Необработанное исключение исполнителя считается критической ошибкой и
логируется с исключением. При отмене активный шаг возвращается в `PENDING`,
а уже завершённые шаги сохраняются. Следующий вызов продолжит обработку.
Последний шаг нельзя пропустить или завершить без итогового ключа: такой
результат останавливает процесс с ошибкой, чтобы видео не стало `READY`
без готового файла.

Перед исполнением шага его `IN_PROGRESS`, `AttemptId` и новая версия процесса
фиксируются в БД. Конкурирующий исполнитель при конфликте не запускает
обработчик. После исполнения состояние шага, видео и метаданные сохраняются
вместе. Для каждого сохранения используется короткая транзакция
`TransactionManager`; внешняя обработка файла идёт вне транзакции.
Ошибка сохранения откатывает изменения БД и останавливает текущий запуск.
При конфликте нужно повторно загрузить процесс в новом DI scope.

`ProcessingContext` передаёт обработчикам рабочий каталог, каталог HLS,
URL исходника, `Metadata`, `FinalKey` и `PreviewKey`. Последний обработчик
должен сохранить реальные файлы в хранилище и передать итоговые ключи.
`ResultData` можно использовать для сохранения данных, необходимых при
возобновлении обработки. Рабочие пути и URL сами по себе не сохраняются в БД.

Конкретные реализации проверки файла, FFmpeg, извлечения превью и загрузки
в S3 подключаются через интерфейс обработчика. Готовых реализаций этих
операций и фонового запуска в текущем модуле нет. Тестовые обработчики
проверяют управление процессом и не выполняют кодирование видео.

## Метаданные и модель видео

`VideoMetadata` остаётся доменным value object: фабрика `Create` проверяет
положительную длительность, ширину и высоту. `VideoAsset.SetMetadata`
разрешён для загруженного видео. Метаданные сохраняются как owned-объект
в nullable-колонках `video_duration`, `video_width`, `video_height`.

Роль упомянутого в конспекте `VideoSet` выполняет существующий `VideoAsset`
с исходником, итоговым файлом, превью и состоянием. Отдельная сущность для
нескольких разрешений не добавляется до появления соответствующего сценария.
Типы домена не переносятся в Core, чтобы не создавать обратную зависимость.

## API состояния

`GET /api/files/{mediaAssetId}/processing` возвращает стандартный envelope
с идентификатором процесса, статусом, прогрессом и упорядоченными шагами.
Для ассета без процесса или удалённого ассета возвращается успешный envelope
с `result: null`.

Существующие API получения медиа возвращают ссылку только для `READY`
с заполненным финальным ключом. Удаление удаляет исходник, готовый файл и превью;
для незавершённого процесса сохраняется состояние `FAILED`.

## EF Core и миграция

Наследование `MediaAsset → VideoAsset / PreviewAsset` остаётся в одной таблице
`media_assets`. `VideoProcess` хранится в `video_processes` со связью один к одному
с видео. `ProcessingStep` — owned-сущность в общей таблице `processing_steps`
со связью один ко многим через `OwnsMany`.

Миграция `20260915171502_AddVideoProcessing`:

- Делает финальный ключ nullable.
- Добавляет исходный ключ, ключ превью, флаг прямой загрузки и токен версии.
- Создаёт процессы и шаги с индексами.
- Помечает прежние ассеты как `DirectUpload = true`, сохраняя их ключи и доступность.
- При откате восстанавливает прежний ключ из `RawKey`, если финальный ключ ещё пуст.

Миграция `20260919121251_AddVideoMetadata` добавляет nullable-колонки
метаданных и не меняет существующие ключи или состояния видео.

Для применения из каталога репозитория:

```powershell
dotnet ef database update --project backend/FileService/FileService.Infrastructure.Postgres --startup-project backend/FileService/FileService.Web
```

В ходе разработки миграция применялась только к изолированным тестовым БД.

## Проверки

```powershell
dotnet test backend/FileService/tests/FileService.IntegrationTests
```

Тесты покрывают доменные переходы, порядок и веса шагов, повторы и критические
ошибки, устаревшие попытки, сохранение и повторную загрузку состояния из PostgreSQL,
конкурентный запуск, multipart-загрузку в MinIO, выдачу финального URL,
удаление всех файлов, прямую загрузку видео и фото, обновление и откат схемы.
Дополнительно проверяются выполнение pipeline, некритические пропуски,
исключения обработчиков, отмена и возобновление, ошибки сохранения,
дублирование обработчиков, сохранение метаданных и освобождение транзакций.

Тесты веб-приложения используют общую xUnit-фикстуру PostgreSQL/MinIO и кеш в памяти.
Зависимость тестового проекта SSH.NET закреплена на 2026.0.0, чтобы устранить
блокировавший сборку аудит NU1903:
[описание исправления](https://github.com/advisories/GHSA-q939-rpr3-3284).
